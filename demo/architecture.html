1 · Data model

One SQLite ledger per job, read-only across boundaries

Each job writes to its own SQLite file in WAL mode, so a 24/7 interface daemon and a year-long warehouse movement ledger never lock each other out. Whenever one job needs another job's history, it opens that file strictly read-only (?mode=ro) or reads the shared morning stock snapshot.

3 · One decision in detail

How the 06:50 agent picks which bins are worth counting today

Counting every rack bin every week is impossible, so the 06:50 engine turns warehouse movements, interface errors, and lot ages into a ranked count list of fixed daily capacity. Splitting that list across risk-ranked, follow-up, capacity-audit, and random exploration lanes fixes today's highest-risk bins while keeping an unbiased baseline to evaluate and train the next model.

Inputs 00_JOB + ro links

  • WMS box & barcode snapshot (every bin, lot code, box qty)
  • 2-hour GR / GI & line-supply stage flow
  • Open ERP–WMS variances & GI interface errors
  • Prior physical count verdicts & adjustment timestamps

Features & noise guards per bin

  • FIFO lot overtaking: newer lots pulled while older box stays
  • Turnover gap: bin dwell days vs part's learned median turnover
  • Vendor relabel guard: blanks false FIFO age when vendor re-stickers old lots
  • Scope & cool-down: low-rack / floor daily; high-rack / secondary facility Saturday

Four lanes fixed daily cap

Lane T · Follow-upYesterday's unadjusted mismatches & mandatory recounts
Lane E · ExploreStratified random sample (stores exact inclusion probability n/N)
Lane P · CapacityLine-side cart slot overflow checks + random normal control
Lane M · ModelRemaining slots filled by highest composite risk score

Feedback loop same day → next run

  • Next morning 06:51 snapshot verifies whether book stock was adjusted
  • Weekly report compares Lane M hit rate against Lane E random baseline
  • Shadow v2 model scores alongside live rules until lift is proven
4 · Logistics data flow & leveling rule

From SRM order to the truck dock — and checking every unloaded box

Supplier portal schedules often bunch too many boxes onto one afternoon truck while leaving earlier trucks half empty, and short deliveries used to be noticed only when the assembly line ran out. Two Logistics agents close that loop: 00_JOB levels portal orders onto fixed trucks without creating a shortage, and 02_JOB checks barcode receipts every 10 minutes so shortfalls trigger a warning before the next truck leaves.

Rule 1 · No shortage ever hard floor

  • Projects stock every 2 hours from the 06:00 ERP + WMS baseline across a 3-day horizon
  • Pulls boxes forward onto an earlier truck whenever stock would drop below zero (or below the 15% arrival buffer) before the next truck
  • Never pushes an order to a later truck — day totals stay equal to the SRM order unless urgent additional boxes are required

Rule 2 · Change SRM as little as possible minimal touch

  • Leaves a supplier's schedule untouched unless a truck exceeds 1.7× the daily truck average (by ≥ 6 boxes) or a physical trailer cap (33 carts on Supplier A)
  • Moves whole boxes forward only for parts keeping ≥ 50% stock margin (relaxing to 100% only when needed to obey a physical trailer cap)
  • Picks the part with the largest movable box count first so the fewest part lines turn yellow

Late SRM order changes PM refresh

  • Re-downloads tomorrow's portal files on demand after an afternoon schedule change
  • Compares each supplier's Truck plan cell by cell against the workbook already sent at 13:40
  • Sends an UPDATED plan (yellow = changed since 13:40) only to suppliers whose plan changed

10-min receipt check per truck

  • Freezes each truck's planned boxes at departure and matches WMS 101 goods-receipt barcodes every 10 minutes
  • Closes a truck after unloading settles and pairs Plan vs Delivered rows (sample file)
  • Writes a plain-English Warning (rounded up to full boxes) only if hybrid stock goes negative before the next carrying truck
5 · Runtime and safety

How autonomous jobs share one workstation without breaking production

Because the agents run on a live workstation alongside ERP and browser sessions, four runtime locks and switches keep background tasks from colliding or posting untested changes. Every code or rule change goes through the same six-step human approval loop before the scheduler is allowed to run it.

Scheduler & morning freeze

21 Windows Task Scheduler slots run around a protected morning freeze window so schema edits or restarts never land mid-run. Bounded worker pools (≤ 1/3 CPU cores, below-normal priority) keep foreground office apps responsive.

ERP & browser mutexes

A file-backed mutex serializes every SAP GUI script across the continuous GI daemon and morning backlog runs, while a single-instance browser rule prevents concurrent WMS or portal sessions from stealing focus or colliding.

Dry-run, switches & worktree block

Posting scripts refuse to execute inside git worktrees, support --no-post / --report-only replay on saved exports, and read JSON switches so risky steps or live external mails can be toggled without editing code.

Online WAL backup & GitGuard

At 03:10 every SQLite ledger is copied via online backup API and verified. Before any commit, GitGuard scans staged diffs to block credentials, internal hostnames, real part/document numbers, and raw data dumps.
